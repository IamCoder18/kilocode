Add a first-class `world` agent tool for browser automation. The agent invokes the tool directly with a `script` parameter (a `;`-separated sequence of browser actions like `navigate ; snapshot ; click --ref e5`) and gets a11y snapshots, evaluate results, and image attachments back. Each session gets its own long-lived browser daemon (auto-started on first call, idle-shut after 5 minutes, stoppable via `world({ script: "daemon.stop" })`). Browser state persists across actions in one call. Computer use is explicitly not shipped in v1.

A screenshot of the page is automatically attached to every world call. If the last action in the script was already a screenshot, that one is reused — otherwise a fresh JPEG (quality 80) is captured and inlined as a `data:image/...;base64,…` attachment so the model can view it without a follow-up `read` call.

The tool is gated by `experimental.world_browser` (defaults to on). Toggle it from the VS Code settings menu under Experimental → "World (Browser and Computer Use)", or from the TUI command palette with `/world` / "Toggle World". When off, the tool is hidden from the agent entirely. The TUI sidebar shows a one-line "World (Browser and Computer Use): Enabled/Disabled" status below Memory.

Three bugs found while smoke-testing the form-fill workflow:

1. **Script parser** — `;` inside quoted strings was treated as a verb separator, so any `evaluate --js "...;..."` with semicolons was chopped. Replaced the tokenizer with a quote-aware single-pass parser that preserves `;` inside `'…'`, `"…"`, or `` `…` ``. Also added `evaluate --js-file <path>` as a reliable way to pass long JavaScript without quoting.
2. **Screenshot byte count** — the `screenshot` field returned by the daemon's dispatcher was dropped by `runViaSession` when mapping the action result, so the tool reported `→ 0 bytes`. `runViaSession` now copies the `screenshot` field through.
3. **Snapshot engine** — `ariaSnapshot({ mode: "ai" })` returned `- document [ref=e1]` for vanilla HTML forms, leaving the agent with 0 refs. Replaced with a DOM walk that produces stable CSS selectors (preferring `#id`), pierces open shadow roots, and redacts names matching `password|secret|pin|otp|token|api[-_]key` to `[REDACTED]`.

4. **Bundle pollution** — `@kilocode/world`'s barrel eagerly re-exported `Runner` and imported `dispatch`, both of which transitively imported `chromium` from `playwright`. That dragged `playwright-core` (and its undeclared runtime dep `chromium-bidi`) into every consumer's bundle, breaking `bun build` for the opencode CLI. `Runner` now lives behind a `@kilocode/world/runner` subpath export and `dispatch` is loaded via `await import()` inside `World.run()`. The daemon process keeps the eager chain since it builds separately with `--external playwright --external chromium-bidi`. `chromium-bidi` is now an explicit dep of `@kilocode/world`.

5. **Daemon shipping** — `DaemonClient` previously looked for the compiled daemon only at `packages/kilo-world/dist/entry.js` (workspace-local), so the tool failed outside dev with "no compiled daemon and bun is unavailable". A new `packages/opencode/script/kilocode/world-daemon.ts` helper bundles the daemon and writes it to `dist/<platform>/bin/world-daemon.js` alongside `kilo`, which means it's automatically copied into both the VS Code extension VSIX (`bin/world-daemon.js`) and the `@kilocode/cli-<platform>` npm package. `DaemonClient.findCompiledEntry()` now checks `$KILO_WORLD_DAEMON_PATH`, then `world-daemon.js` next to `process.execPath`, then the workspace dist fallback. `kilo-vscode/script/local-bin.ts` hashes `kilo-world` so daemon source changes trigger an extension rebuild.

6. **Runtime install** — `playwright` and `chromium-bidi` are externalized from both the opencode binary and the daemon bundle (Playwright does not declare `chromium-bidi` in its own `dependencies`). A new `WorldRuntime.ensure()` in `packages/opencode/src/kilocode/world-runtime.ts` mirrors the `LanceDBRuntime` pattern: it lazily installs `playwright@1.61.1` and `chromium-bidi@^12.0.0` into `~/.cache/opencode/packages/<pkg>/node_modules` via `Npm.add` on first use, then sets `$KILO_WORLD_NODE_PATH` so the spawned daemon can resolve bare `playwright` / `chromium-bidi` specifiers. The world tool awaits `ensure()` once per invocation (cached after first call). Browser binaries (~150 MB) still need a separate `npx playwright install chromium` step on first launch; the daemon's `status` verb reports the download state.

7. **Daemon-server dispatch chain** — `daemon/server.ts` previously eagerly imported `dispatch` from `./dispatch` even though it's only used inside `handleLine` for non-control-plane verbs. That pulled the entire browser-command chain (`dispatch` → 17 commands → `Runner` → `playwright`) into the opencode bundle via the barrel → `DaemonClient` → `DaemonServer` path. `dispatch` is now loaded via `await import("./dispatch")` inside `handleLine`, matching the lazy pattern used in the barrel's `World.run()`. The daemon process is unaffected — its bundle builds fine with the lazy import, and `dispatch` loads on first request.

8. **Bundle-graph traversal through dynamic imports** — Bun's bundler follows string-literal dynamic `import()` calls when tracing the module graph. Even after the previous fixes, `daemon/dispatch.ts` statically imported all 17 browser command classes (and `Runner`), so the opencode bundle still contained `import { chromium } from "playwright"` and crashed at startup with "Cannot find package 'playwright'". Both `daemon/dispatch.ts` and `dispatcher.ts` are rewritten so each command is loaded via `cmd(specifier, key)` — a helper that does `import(/* @vite-ignore */ specifier)` where `specifier` is a runtime variable. Bun's bundler can't statically resolve variable specifiers, so the chain to `playwright` is now severed at the dispatch layer. The daemon process still loads commands on first request. Verified: opencode binary starts cleanly (`kilo --version` → exit 0), `grep "playwright"` in the binary returns 0 matches.

9. **Daemon-runtime ESM resolution** — Even after fix #8 (which only hid the chain from the opencode bundle), the daemon process at runtime failed with `Cannot find package 'playwright'` because Node's ESM resolver ignores `NODE_PATH` and `cwd` — it only walks up from the importing module's directory looking for `node_modules/<specifier>`. Two consequences:

   a. **`setDispatch(fn)` injection** — `daemon/server.ts` no longer holds a `await import("./dispatch")` call. Instead it exposes `setDispatch(fn)` and reads the active dispatcher from a module-level `installedDispatch` variable. The daemon's `entry.ts` calls `setDispatch(dispatch)` immediately after import. This means `server.ts` (reachable from opencode's barrel via `DaemonClient`) no longer references `daemon/dispatch.ts` at all, so the opencode bundle stays clean. The daemon bundle statically includes `entry.ts → dispatch.ts → commands → Runner → playwright`.

   b. **Bundle playwright + chromium-bidi into the daemon** — `world-daemon.ts` no longer externalizes `playwright` and `chromium-bidi`. Node's ESM resolver would otherwise fail to find them at the daemon bundle's location. The daemon is now self-contained at ~3.7 MB (`world-daemon.js`) and runs anywhere without any runtime dependency setup. The `LanceDBRuntime` install pattern is still used by `WorldRuntime` but is no longer needed for resolution — it remains for documentation and so a future browser-bootstrap step (e.g., `npx playwright install chromium`) can hook in via the same cache dir.

Verified end-to-end on Linux: opencode smoke test (`kilo --version`) passes, `grep "from\"playwright\""` in the opencode binary returns 0 matches, daemon listens on its unix socket, the `status` verb returns `chromiumReady: true` with Chromium 149.0.7827.55 detected.

10. **Daemon lookup breadth + bun availability** — `DaemonClient.ensureRunning()` was brittle: `findCompiledEntry()` checked only `dirname(process.execPath)/world-daemon.js` and the workspace dist fallback (which fails when `import.meta.url` resolves to a bunfs path inside a compiled binary). The `isBun` check used `process.execPath.endsWith("bun")`, which is false for Bun-compiled binaries whose executable is named `kilo`. Now: `findCompiledEntry()` checks `KILO_WORLD_DAEMON_PATH` → `dirname(process.execPath)/world-daemon.js` → `dirname(process.argv[1])/world-daemon.js` → `packages/kilo-world/dist/entry.js`. `bunAvailable` uses `Bun.which("bun") !== null` (works in compiled binaries via bunfs). The error message lists every path tried plus the rebuild instruction, so a missing-daemon failure tells the user exactly where to drop `world-daemon.js` or which env var to set.

11. **Windows console flash + diagnostic log path** — `spawn()` for the daemon lacked `windowsHide: true`, so every `world()` invocation flashed a cmd.exe window at the user for the daemon's lifetime on Windows. Added the flag (stdio is already redirected to the log file via `openSync(..., "a")`, so the window served no purpose). Also extended the 30-second startup-timeout error to include `DaemonServer.logPath(sessionID)` so the user can read why the daemon actually died instead of guessing.

12. **Ship `world-daemon.js` in the VS Code extension** — `packages/kilo-vscode/script/local-bin.ts` and `script/build.ts` only copied tree-sitter, sandbox, and the sandbox worker into `packages/kilo-vscode/bin/` alongside `kilo.exe`. The `world-daemon.js` (3.7 MB self-contained daemon with playwright + chromium-bidi bundled in) never made it into the VSIX, so the extension's bundled `kilo.exe` couldn't find its daemon at runtime and fell back to the broken source path. Added `copyWorldDaemon()`/`hasWorldDaemon()`/`worldDaemonForBinary()` helpers in `cli-resources.ts` and called them from both `local-bin.ts` and `script/build.ts`. `local-bin.ts`'s `ready` check now also requires `hasWorldDaemon` so an extension rebuild re-runs when the daemon changes.

13. **TCP localhost instead of Unix sockets (Windows fix)** — the daemon's IPC was a Unix domain socket at `~/.local/state/kilo-world/daemon-<session>.sock`. On Windows, Node 22+ emulates Unix sockets via named pipes but the `\.local\state\...sock` path triggered `listen EACCES: permission denied` at daemon startup, causing the 30-second timeout. Switched to **TCP localhost** with `server.listen({ host: "127.0.0.1", port: 0 })` (OS-assigned port). The handshake file now carries `{ host, port }` instead of `{ socketPath }`; the client reads the handshake and connects via `createConnection({ host, port })`. The legacy `.sock` filename is kept as a derived name for log-file derivation only — no actual socket file is created. Verified end-to-end on Linux: daemon listens on `127.0.0.1:33039`, handshake has `{host, port}`, TCP connect returns daemon status.

14. **Per-daemon auth token** — TCP localhost alone isn't safe on multi-user systems: any other local process running as the same user can connect to `127.0.0.1:<port>` and drive the browser. The daemon now generates a 32-byte hex token at startup (`randomBytes(32).toString("hex")`), writes it to the handshake file alongside `{host, port}`, and requires `req.auth === token` on every inbound request — including `__ping__` and `__status__`, so there are no anonymous reads. The server closes the socket on mismatch, before the request reaches the dispatch layer. The `DaemonClient.send()` helper reads the handshake once per call and tags every outgoing request with `auth: hs.token`. The model follows the opencode CLI server's auth middleware (`packages/opencode/src/server/routes/instance/httpapi/middleware/authorization.ts`), which checks `ServerAuth.authorized(credential, config)` per request — same shape, different transport (we're raw TCP, they're HTTP Basic / `?auth_token=`). Verified: no-auth and wrong-auth both cause the server to close the socket; correct auth returns daemon status normally.

15. **Hardcoded 15s per-segment timeout** — `DaemonClient.runViaSession` called each per-segment action with `timeoutMs: 15_000` regardless of the world tool's `timeout` parameter, so first-time navigation against a freshly downloaded Chromium could not complete. The hardcode is replaced with `opts.timeoutMs ?? 60_000`, and the world tool now threads its `params.timeout` (default 60s) through to `runViaSession`. The overall abort timer still caps the whole run.
